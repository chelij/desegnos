# Desegnos 1.0 release plan

Updated 19 October 2026. Desegnos is the product name selected after Cipta and Desegni. This document specifies the complete first public release, its implementation order, estimate, and evidence required to ship it. Current implemented behavior and verification are recorded separately in [docs/IMPLEMENTATION.md](docs/IMPLEMENTATION.md).

Desegnos is a free, open-source desktop website editor with a Rust core. Users draw areas on an empty page, describe what belongs there, generate with their own OpenAI key, and continue editing visually. The complete release includes multi-page projects, reusable components, shared styles, a project brief, interaction and form states, real image generation, custom JavaScript and React components, fonts and media, search and sharing metadata, persistent version history, a pre-export site check, and both portable web and React exports.

Desegnos itself maintains a private PROJECT.md from accepted user decisions. Clicking Generate makes an immutable REQUIREMENTS.md and sends that actual Markdown file to the AI agent. Generation separates site implementation, verified React component reuse, and identity requirements. Design criticism explains concrete clashes while allowing intentional creative choices. These are application behaviors to implement, not Markdown files the developer creates manually for each user's website.

The editor has no sidebars. Users type plain prompt text boxes directly on the website canvas, like a client pointing at where something belongs. Fuzzy/Strict is one generation setting beside Generate. Annotation placement communicates intent; the agent coordinates the actual website layout and responsive dimensions.

4. Complete Tier 2: responsive preview/per-size requests, authoritative global styles, generated/stock images and one real publishing provider.

## 3. User experience

### Creating a document

Creating a project first offers Blank website, Use my existing brand, Open project and recent projects, then asks for a project name, Web/Mobile and resolution. Web starts at 1440 × 900 CSS pixels and mobile at 390 × 844, with common screen presets and custom dimensions. Every new project starts light. A compact Light/Dark control changes the current page afterward. Height is an initial screen guide and a page can grow beyond it. These are web preview dimensions.

Identity import accepts Desegnos project archives, website folders and ZIPs. Collection is read-only and bounded, excludes secrets and dependency/build files, rejects unsafe archive paths and never executes source. Users inspect selected files before explicitly requesting AI analysis with their configured provider. Strictly validated findings include source references and confidence; portable logo candidates carry actual checked image bytes. Creation records only approved findings and logos in core identity memory, PROJECT.md metadata and future generation requirements, while opening a blank light canvas. Cancellation, interrupted outcomes, explicit retries, stale analysis and save/reopen integrity are acceptance requirements. The importer is a core identity workflow; adapters may add source formats without gaining file-system or provider authority.

The workspace starts entirely empty, even when a project brief or logo exists. A screen outline provides a reference rather than restricting placement. Requests can be placed above, below, or on either side of it. The grid starts on at an 8 CSS-pixel interval; users can choose pixel or percentage spacing and independently control visibility, snapping, and rulers. Rulers default to pixels with percent available independently. Guides, rulers, zoom, pan, and selection overlays never appear in exports. The editor theme follows the operating system by default and can be changed separately from the site's appearance. The brief lives in the project dossier and introduces no extra initial content-creation tool.

The canvas fills the workspace. Browser-style tabs switch project pages. One nested menu holds project/file, editing, page, view, and technical commands. The top bar keeps the project identity, AI connection, and generation controls. The default interface uses short nontechnical labels; raw Markdown, source, digests, detailed model settings, and diagnostics are available through menus. Project dossier, assets, history, settings, and detailed tools open as dialogs or contextual controls. They must not become permanent sidebars or move prompt entry away from the workspace.

### Describing areas

Left-button dragging pans the workspace. Shift+drag marks an area and focuses a plain multiline text box at that location, directly over the site. Clicking another selection dismisses an abandoned empty box without losing typed requests or undo history. Ctrl+wheel zooms around the pointer. Users type the description there. Double-clicking empty canvas space or a generated element opens its prompt; a single click selects and outlines the generated element with contextual direct-edit controls and opens no prompt. Keyboard placement must also work. Prompt text remains editable on the canvas; there is no separate prompt inspector, per-box mode selector, or coordinate form. Minimal contextual move/resize/remove affordances must preserve normal text selection, caret movement, input methods, and accessible keyboard editing. An empty description never starts a generation job. Standard shortcuts include New/Open/Save/Save as, project Undo/Redo, zoom in/out, fit guide, actual size, 200%, page-tab cycling, selected-request deletion with confirmation, Escape, and discoverable shortcut help. Text fields retain text editing, clipboard, input-method and text-history behavior.

Annotations use stable region identifiers and placement rectangles in document CSS pixels so zoom, scrolling, and monitor DPI preserve their intent. These coordinates are internal context, not requested website bounds or fields the user must enter. Overlapping annotations remain independently editable. Focus cycling and contextual ordering controls make obscured prompts reachable without a sidebar. Moving or resizing a prompt changes the hint sent to the agent; it does not directly move or resize generated site content.

Generate stays visible in the top bar, disabled until a trimmed prompt is nonempty anywhere in the project, beside the Flexible/Precise interpretation dropdown. Fuzzy is the default and the selected mode is remembered and frozen for each job. One click prepares and submits the job using the configured account/key and request allowance. A nonmodal horizontal progress strip shows activity and Cancel, while only submitted elements or areas blur. Users can keep editing; unfinished inline text is committed before automatic apply so stale output cannot overwrite it. Raw requirements, scope, cost/plan information and diagnostics are available through Details and its nested menu. It submits all filled prompts with page IDs, signed placement and percentage hints relative to the screen guide, ordering, global mode, and relevant preferences. A missing connection opens provider setup while preserving prompts. The button cannot submit the same job twice.

### Fuzzy and Strict

| Mode | Placement intent | Interpretation |
| --- | --- | --- |
| Fuzzy | The agent uses the annotation's location as a composition hint and may reorganize for coherence and responsiveness. | The AI has more freedom where the description leaves room, while preserving explicit requirements and protected decisions. |
| Strict | The agent follows requested relative placement, reading order, and grouping closely, and coordinates usable dimensions and responsive behavior. | Follow the descriptions closely; surface contradictory or missing requirements rather than substituting content or silently relaxing them. |

The mode belongs to the generation job, never to an individual annotation. Neither mode treats the text box's outer rectangle as an exact website element boundary. The agent turns the descriptions and spatial hints into explicit responsive layout constraints and explains material departures in the generated dossier and optional details. Natural-language and relative-placement fidelity require evidence, AI evaluation, and user review; schema validation cannot prove every semantic requirement.

When content, explicit dimensions in a description, placement intent, or protected rules cannot coexist, show the conflict with actions to revise the description or deliberately change the relevant requirement. Moving or resizing the annotation can clarify intent but is not a required fix for text-box capacity. Do not silently remove requested content, shrink text until unreadable, or clip essential controls. The agent remains responsible for fitting and coordinating the actual page at every supported width.

### Generating and revising on the canvas

The progress window identifies the actual current step: preparing, generating layout, generating approved images, compiling, validating, or updating the canvas. Users can cancel or dismiss and reopen progress without resubmitting. Blur is limited to the frozen submitted targets, never the entire workspace. Unaffected content stays sharp.

Valid, conflict-free output replaces the affected site content directly after current-requirement validation and a durable safety checkpoint. Checkpoint or validation failure leaves the current site intact. Application commits the generated source and completed-request status atomically, updates the project brief, and shows an on-canvas Keep/Undo/Try again/Details bar. Undo and Try again can revert that exact applied revision only; newer local edits dismiss its review controls. Submitted drafts stay in history and can return with Undo. New identity rules remain advisory until explicitly accepted. Cancellation, uncertain outcome, refusal or error retains the current site and editable requests. Retrying a provider request always requires an explicit user action; neither reopening progress nor Undo/Redo submits it again. Technical receipt and failure details remain optional menu content, not an approval screen in the normal generation flow.

A user double-clicks a rendered element to open a plain revision prompt beside it, or draws another area for new content. Element targets carry a source fingerprint, structural selector, label and geometry in the frozen requirements file. Selecting another element without typing replaces the empty selection while preserving any filled requests. Keyboard selection must cycle past nested text and icon content and allow choosing a parent. Generated website scripts stay paused during selection; explicit interactive preview remains separate. Undo restores the last generated site and its requests as one transaction. The full canonical document release must enforce targeted subtree and shared-definition impact; the current HTML generation gate passes complete affected-page source with the target and validates the complete returned page. An overlapping new area does not implicitly authorize deleting what is underneath.

### Editing and previewing

Provide direct text editing through a trusted editor overlay, not an editable generated document. Support Unicode, input methods, multiline text, links, heading levels, labels, alternative text, and semantic element choice.

Contextual visual tools and dialogs cover typography, text and background colors, borders, radius, shadow, spacing, dimensions, alignment, flex and grid layout, visibility, positioning, stacking, image crop, links, media properties, and form properties. These inspect actual generated content, not prompt coordinates, and never dock into a sidebar. Keyboard commands provide pointer alternatives. Changes clearly apply to a component definition or instance, base style or breakpoint, and selected interaction state.

An on-demand layer organizer supports rename, select, reorder, group, ungroup, compatible reparenting, duplicate, delete, lock, and hide without occupying a sidebar. Dragging generated content in a flow layout changes order or layout constraints; dragging an explicitly positioned site layer changes its coordinates. Distinguish these operations from moving prompt annotations. A custom component's wrapper supports them while its internal code remains AI editable.

Editing mode prioritizes selection; Preview mode forwards normal pointer and keyboard input to the page. Preview supports arbitrary viewport widths, desktop/mobile presets, and a detached native window. Read-only source views provide a file navigator for the actual generated page/component, style, script, and metadata files in each export format. All enabled controls must produce an observable, undoable change or a clear validation message.

### Responsive behavior

Store base styles and explicit breakpoint overrides. Default review widths are 390, 768, 1024, and 1440 CSS pixels, plus the user's reference width and 320 for minimum-width checking. Users can add breakpoints and edit the layouts at them.

Annotations supply placement hints. Generated content has explicit responsive constraints: size rules, parent relationships, reading order, alignment, and intentional overlays. The agent coordinates those constraints using all requested areas and accepted site identity. The compiler uses flex/grid for flow content and positioned wrappers for intentional overlays; it must not flatten the page into a scaled image or fixed desktop screenshot, or hard-code the prompt text box rectangles as site geometry.

For an unspecified narrow layout, independent content areas stack in document reading order with 16-pixel page padding and gaps. Intentional overlays remain grouped and anchored to their container. The candidate must include explicit overrides when this default would lose meaning. Desktop and intermediate widths must have actual constraints, not a single mobile screenshot. Unintended overflow, obscured controls, or contradictory explicit requirements block Apply until resolved; text-box capacity is not a site constraint.

### Pages and navigation

A top-bar page selector and Pages dialog support add blank page, duplicate, rename, reorder, group into path folders, choose home page, choose 404 page, and include/exclude from export. A new project has one empty home page; a 404 page is added and edited through the same tools. Page names are independent of public paths. Require one included home page and unique normalized paths. Reject traversal, reserved output directories, and case-insensitive collisions that would break Windows exports.

Internal links store page IDs and optional stable anchor IDs, not handwritten filenames. Changing a page path or anchor label regenerates all affected internal links and menus. Show the affected references before deleting a linked page, anchor, or component; require replacement or removal of those links in the same transaction. Link selection supports another page, a section, a configured external URL, email, telephone, and a project download asset. Validate the corresponding URL scheme and resource type.

Navigation components use actual included pages, allow user-controlled order and labels, and have current-page, mobile-menu, and keyboard-focus behavior. Preview follows internal links through the frozen accepted or candidate site without leaving the restricted preview. Source and export commands operate on the full included site; a clearly labelled page-only export may be offered in addition and must warn about links to omitted pages.

### Project brief and protected content

Project settings expose a versioned brief with site purpose, audience, brand/business name, factual copy, tone of voice, chosen languages, logo assets, palette, font assets/fallbacks, spacing preferences, reference images, and specific content the AI must preserve. Each field is optional unless a requested behavior requires it. Users can attach references per project or per region. References inform generation but are not automatically inserted into a page or exported.

Separate preferences from enforceable protection rules. A rule can preserve exact text, an asset hash, a node/subtree, or a layout property. The rule records the protected target and allowed changes. Enforce these rules in Rust against candidate patches, including changes reached through shared definitions. These guarantees cover the persisted model and declared asset references. Render checks also flag observed violations; arbitrary custom-code behavior still requires review. Layer locking for pointer editing is a separate control. User-driven manual changes and explicitly changing/unlocking a protection rule remain possible and undoable.

Security boundaries, permitted edit scope, and protected content cannot be overridden by Fuzzy mode. Region descriptions may refine brief preferences, but a conflict with a protected fact or rule must show the rule and require a deliberate brief edit or unlock. Imported references are task data and cannot supply permissions. AI suggestions must not invent business facts, legal claims, customers, testimonials, or metrics to fill a page.

The generation review lists which brief fields, references, and rules were used. Only relevant assets are transmitted; video/audio files and unrelated pages are not automatically uploaded. A brief or protection change invalidates in-flight candidates that depend on it. Export reachability excludes brief-only references, internal notes, and generation history.

### Project memory maintained by Desegnos

Desegnos creates PROJECT.md inside each saved project archive and exposes it through Project dossier. It contains the accepted purpose/audience, factual identity, logo and asset references, shared palette/typography, reusable design patterns, functional requirements, decisions, and intentional exceptions. Omit unknown facts and empty sections. Do not fill them with invented business details or generic sample copy.

The canonical brief, tokens, protection rules, and decision records remain typed project data. PROJECT.md is their deterministic, human-readable projection, generated by Desegnos rather than by a free-form AI rewrite. This avoids a second source of truth. Decision records contain a stable ID, scope, accepted value, source action, revision, and optional rationale. References point to stable project IDs and asset hashes rather than machine-specific paths.

Manual user choices update the corresponding records immediately. Every complete, validated generation automatically updates the dossier with its actual summary, identity proposals, advisory feedback, target IDs, attempt, and requirement/candidate digests. Draft records remain explicitly distinct from accepted requirements. This bookkeeping is durable, idempotent, preserves ongoing edits and undo/redo, and cannot replace the current dossier with an obsolete response. Local save recovery never resubmits a provider request.

Compatible proposals start selected in the review, and users can uncheck them. An AI proposal becomes an accepted choice only when the user applies the review containing that selected proposal. The same Apply transaction commits the site changes, shared identity changes within the approved scope, and decision records. Conflicting accepted or protected rules are never silently overwritten. Discarded candidates, tentative interpretations, and rejected design advice never become accepted requirements. The dossier records whether the last generated site is a draft, applied, or undone, and relevant draft context sent to future generation is explicitly nonbinding.

Users can correct or remove a decision through Project dossier and brief/style controls. Free-form notes remain identifiable as user notes; they do not silently replace protected facts or grant capabilities. Undo, autosave, save/reopen, recovery, and checkpoint restoration keep the typed records and generated Markdown consistent. Restoring project memory invalidates dependent generation jobs without rewinding paid-job records.

PROJECT.md is private project material. It is excluded from public HTML and React site exports. A user can explicitly copy/export the notes or remove them from a shareable project copy. Generate includes the relevant accepted decisions in its requirements snapshot; unrelated private notes and assets are not transmitted automatically.

### Design criticism and creative control

Desegnos gives feedback when a candidate or accepted design clashes with an explicit identity rule, creates inconsistent shared styling, harms readability, obscures controls, breaks responsive behavior, or makes an interaction difficult to use. A finding identifies the affected element/page, viewport/state, concrete observation, likely effect, and a specific alternative. Measurements and observed failures are distinguished from qualitative design judgment. A style opinion cannot be presented as a measured accessibility result.

Advisory findings offer Keep this design and Review alternatives. Keeping a deliberate choice can record a scoped intentional exception, with the user's reason if supplied, in PROJECT.md. Subsequent AI work respects that exception. A page-specific experimental palette does not change the site's palette. Reconsider an exception when its target, underlying rule, or material conditions change; do not repeatedly nag about the same accepted choice.

Creative advice does not become an export blocker merely because the AI prefers a conventional layout. Genuine invalid project state, broken required behavior, protected-content conflicts, and unmet Strict requirements retain their existing checks. Users can explicitly revise those requirements or protections through the normal controls. Advice cannot automatically restyle the project, unlock content, or switch Strict to Fuzzy.

Run inexpensive structural/render checks during ordinary editing. Include qualitative criticism in the generation review, and provide an explicit Review design action for a further paid AI review with visible scope and estimated cost. Do not make a paid request on every keystroke. In uncertain cases, explain what needs checking instead of inventing a defect or a clean bill of health.

### Reusable components and shared styles

Users can turn selected standard nodes into a reusable component, create linked instances, edit its definition, expose typed properties, choose named variants, override instance content/styles, reset overrides, and detach an instance into ordinary nodes. Reusable headers, footers, buttons, cards, and saved sections use this same mechanism. Copying a saved section into a local library or another project copies its required definitions and asset bytes, remaps IDs, and validates dependencies; it never depends on the source project's disk location. Custom component code stays restricted when reused.

Definition edits show every affected instance and page before committing. Instance edits create local overrides unless the user explicitly enters definition editing. Removing a definition requires replacing or detaching its instances. Disallow component-reference cycles. Rendered node addresses include both the instance and definition-node identity so selecting one instance cannot edit another accidentally. Resolve internal IDs per instance and validate page anchor uniqueness.

The shared-style editor manages named semantic colors, font families, typography scales, spacing, radii, and shadows. Values can vary by page appearance and breakpoint. Deleting or changing a used token shows references and requires replacement or a deliberate shared change. New AI work uses the brief and existing tokens; it cannot restyle the whole site during a scoped area edit.

Resolve styles deterministically: definition defaults, instance overrides, breakpoint overrides, interaction-state overrides, then explicit combined breakpoint/state overrides. Tokens supply values rather than changing that precedence. Contextual style tools show the value's source and provide reset-to-inherited actions. Both compilers and both exports use the same resolution rules.

### Interaction states and forms

Contextual style controls support normal, hover, keyboard focus, pressed, and disabled states. Components and forms also support real loading, empty, success, and error states where their behavior defines them. Users can force a state for inspection inside the editor; those forcing controls and attributes are removed from exports. Exported CSS uses real browser selectors and the component's real runtime state. Respect reduced-motion preferences and test the state combinations at relevant breakpoints.

The form builder edits field type, name, label, help text, required status, autocomplete, option values, and appropriate length/range/pattern constraints. Support native HTML validation and declared cross-field rules with accessible error messages. Client checks improve feedback; the real endpoint must still validate submitted data, as [MDN's validation guidance](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Constraint_validation) explains.

Each form binding specifies the actual destination, method, encoding, field mapping, and response contract. Support ordinary GET/POST form navigation and browser fetch-based JSON/form submission; never silently switch methods or destinations after failure. Fetch forms have idle, validating, submitting, success, error, and uncertain-outcome handling. Disable duplicate submission while pending, preserve entered values on failure, and show success only after the declared response condition actually succeeds. Do not automatically retry write requests without a real endpoint's tested idempotency contract.

Missing destinations are explicit configuration findings: the editor shows that submission is unconfigured, offers the binding controls, and prevents presenting an enabled working submit action. Publication export is blocked for an included unconfigured form. AI requests requiring a functional form remain conflicted until the user provides the real binding. Preview requests must satisfy browser CORS and sandbox policies; test the exported origin as well. Use a controlled real test endpoint during release verification. Submission values and responses are runtime data and must not enter the project archive, history, or diagnostics by default.

## 4. Architecture and dependencies

Use Tauri 2 for the desktop shell, Rust for durable state and privileged operations, and React with TypeScript for the editor interface. Tauri's [process model](https://v2.tauri.app/concept/process-model/) supports this separation. Use native browser Pointer Events and DOM APIs for selection and direct manipulation.

Choose established libraries for concrete needs. Do not add packages to make a stack look complete, recommend unrelated libraries, or interpret popularity as a security guarantee.

| Responsibility | Selected technology | Reason |
| --- | --- | --- |
| Desktop shell | Tauri 2 and its official dialog, opener, and updater plugins | Rust integration and native packaging with explicit permissions. |
| Editor UI and build | React, TypeScript, Vite, pnpm | Maintained tooling and the same component language as the React export. |
| Rust serialization and networking | Serde, Tokio, [reqwest](https://docs.rs/reqwest/latest/reqwest/) with rustls | Typed document contracts, cancellation, and direct streaming HTTPS. |
| Credentials | Rust keyring crate backed by native credential stores | Avoid writing API keys to project files or ordinary configuration. |
| Read-only source | CodeMirror 6 | Accessible, selectable, highlighted source without creating an unsupported source editor. |
| Qualified React components | Radix Primitives: Dialog, Tabs, and Accordion in the initial catalogue | Reuse established interaction primitives while styling them with the project's identity tokens. Only qualified, pinned entries are available to generated code. |
| Custom component compilation | esbuild-wasm in a Web Worker | Actual JSX/TSX compilation and bundling without running a shell or npm inside the application. |
| Archive persistence | Rust [zip](https://docs.rs/zip/latest/zip/) crate and RustCrypto [sha2](https://github.com/RustCrypto/hashes/tree/master/sha2) | Portable projects with bounded extraction and SHA-256 asset integrity. |
| SVG input | DOMPurify with a restricted SVG profile and resource-reference validation | Sanitize imported vector assets before preview or export. |
| Raster optimization | Rust [image](https://docs.rs/image/latest/image/) crate for decoding/resizing/JPEG/PNG/ICO, and Google's [libwebp](https://developers.google.com/speed/webp/docs/api) for WebP encoding | Generate real quality-controlled lossy/lossless variants while retaining originals. |
| Verification | Rust tests, Vitest, WebdriverIO's Tauri service, Playwright for exported browser pages | Domain checks, actual native workflows, and export behavior across browser engines. |

Pin exact resolved versions at the foundation stage and commit `Cargo.lock`, the pnpm lockfile, a Rust toolchain file, and the package-manager version. Verify maintenance, licenses, security advisories, and native compatibility before adoption. Version selection is an implementation deliverable, not a floating dependency in a release build.

Pin and checksum the official libwebp source and compile the encoding library into native packages through a narrow Rust FFI boundary. Validate dimensions, strides, buffer lengths, allocation/free paths, and cancellation; test it on the native matrix. It needs no runtime download or shell invocation. Enable only required image-crate formats, and keep the native codec in the editor rather than exported browser code.

The first custom-code module catalogue contains React, React DOM, and the project's small export helpers. Save `.desegni` as a ZIP-based project with a manifest, versioned project/page/component JSON, assets addressed by content hash, custom modules, a content-addressed snapshot store, checkpoint index, and a small generation provenance ledger. Original and optimized assets are separate immutable objects with derivation metadata. Keep API keys, HTTP authorization headers, machine-specific absolute paths, provider response bodies, and form submission data out of the archive. Account for temporary files, recovery records, and the previous-save backup when checking free space. Report the specific limit rather than crashing. These are documented aggregate support limits and may be raised only with relevant tests.

Writes go to a same-directory temporary file, sync its contents to disk before atomic replacement, sync the directory where supported, and keep the preceding valid save as a named backup. Preserve the original if replacement fails. Rust durably journals each accepted transaction before acknowledging it as committed, checkpoints recovery data after at most two seconds of idle time, and records the clean-save revision. On restart, offer the recovered version alongside the last explicit save, with timestamps and a discard action. Do not overwrite the original during recovery.

Opening a project with a newer unsupported schema provides a clear refusal without modifying it. Supported migrations copy the original first, validate the result, and retain the backup. A per-project write lock prevents two editor windows from silently overwriting each other; a second opening is read-only or explicitly takes over after the old writer closes.

Undo/redo includes page/path/navigation edits, component definitions and overrides, brief/protection changes, visual edits, regions, shared styles, form bindings, assets, and generation Apply. Cross-page operations are one project transaction. Persist enough journal information to recover committed unsaved changes after a crash. Keep 200 undo transactions per open project; reclaim unreferenced objects only after they leave the current project, retained undo history, checkpoint history, candidate/paid-asset jobs, local library, and recovery records.

PROJECT.md is derived from versioned decision records and the current brief/style data. Each generation job records the exact REQUIREMENTS.md bytes, SHA-256, source revision, document-format version, target/dependency hashes, attachment manifest, and resolved catalogue entries. Requirements artifacts are private, content-addressed job data retained with the relevant job/history records and governed by project storage and pruning limits. Record these dependencies with the project so it can reopen and export without resolving a floating latest version. ## 6. AI generation and scoped changes

### Three responsibilities for each request

Classify each filled input by the work it requires. The categories can overlap; a branded dialog can require all three. These are responsibilities within Desegnos's generation workflow and do not require three separately running agents.

| Responsibility | Required behavior | Result |
| --- | --- | --- |
| Implement the website | Write actual browser JavaScript/React where needed and produce the typed page/component/style changes that the compiler turns into HTML, CSS, JavaScript, and React source. | A runnable candidate with actual behavior and asset references, scoped to the requested areas. |
| Find and reuse React components | Recognize the needed behavior, query the qualified catalogue and existing project components, verify the actual supported API, and reuse an appropriate match. | Verified component IDs/versions, selection reasons, declared dependencies, and real integration code. |
| Identify identity requirements | Detect supplied facts and choices that should remain consistent, compare them with accepted project decisions, and separate site-wide requirements from local styling. | Reused identity constraints, proposed new decisions, or explicit conflicts for review. |

An AI's recollection that a library has a component is a lookup lead, not proof of an available API. The host resolves catalogue entries and rejects invented package names, exports, properties, or unqualified imports. Prefer existing project definitions and suitable native HTML before introducing a library. A local instruction such as changing one button's color does not authorize changing a shared brand token. New shared identity rules and inferred identity suggestions are visible proposals until accepted in the appropriate scope.

### Requirements Markdown sent on Generate

When Generate is clicked, Desegnos validates and freezes the current request, then creates REQUIREMENTS.md itself. This is the actual requirements document supplied to the agent; users do not write it manually. The document is readable in a What will be sent view, with the selected provider/model, attachment list, scope, and estimated cost. The first-request content disclosure remains part of the existing BYOK flow.

The document contains these sections when applicable:

1. Request identity: job ID, project revision, requirements-format version, one frozen Fuzzy/Strict generation setting, allowed target IDs, and explicitly permitted shared changes.
2. Accepted project requirements: purpose/audience, relevant PROJECT.md decisions, identity tokens, protected facts/assets/subtrees, and intentional exceptions, each with its scope.
3. Every filled pending area: page/region IDs, exact prompt text, placement hint in CSS pixels, annotation order, reference resolution, page appearance, and responsive expectations. Explain that position suggests intent and the agent coordinates actual dimensions and layout.
4. Relevant implementation context: current target content/source, shared components and overrides, links/routes/anchors, state/form contracts, supported browser behavior, and the required output contract.
5. Available components and assets: qualified catalogue entries and project definitions, verified symbols/props, asset IDs/hashes, separate image attachments, and declared public endpoint bindings.
6. Acceptance conditions: target coverage, fidelity to descriptions and relative placement under the selected job mode, identity/protection consistency, actual interactions, responsive preview/export parity, expected critique, and unresolved inputs that must become explicit conflicts. There is no one-pixel match test against annotation text boxes.

Exact values and identifiers come from validated project data. Preserve prompt text as delimited task data; escape Markdown boundaries so a prompt cannot impersonate another section. There is no silent summarization of required regions, protections, or deliberate exceptions. If the complete required context exceeds limits, show a scope/size conflict before sending. Large unrelated history and private notes are excluded rather than uploaded wholesale.

The OpenAI adapter sends REQUIREMENTS.md as an actual Responses API input_file with its filename and Base64 file_data, using UTF-8 Markdown bytes. The [official file-input documentation](https://developers.openai.com/api/docs/guides/file-inputs) supports Markdown and Base64 file inputs through Responses. No separate hosted file URL or persistent Files upload is needed for this route. Non-PDF file processing extracts text, so relevant image references also require separate supported image inputs; a filename inside Markdown is not a substitute for the actual image.

All planning, implementation, and critique steps use the same frozen document and hash. Verified component-resolution results and candidate measurements can accompany subsequent steps, but cannot rewrite the original requirements or enlarge permissions. The host persists job intent before paid calls and accounts for every planning/implementation/review call. The requirements hash identifies the snapshot; it does not prove the AI complied. Native validation and candidate review establish that.

### Candidate generation and application

The immutable generation request includes a local job ID, base project revision, prompt-template version, provider/model, one global generation mode, page IDs and viewports/appearance, relevant brief fields and protection rules, resolved design tokens, referenced component definitions and instance overrides, interaction/form contracts, selected target IDs, every filled pending region across pages, placement hints, annotation order, and relevant assets. Include a compact route/navigation context and only the content dependencies needed for the requested work. Asset images are sent only when relevant to the user's request; disclose what content goes to the provider before the first request. Required context that exceeds a request limit produces an actionable size/scope conflict; never silently drop a protected rule or filled region.

Treat page text, imported metadata, and reference assets as untrusted task data. They cannot expand the user's target scope, enable tools, request secrets, change endpoints, or authorize shell execution.

Use the OpenAI Responses API with strict JSON Schema output for a typed candidate patch. This uses `text.format`, rather than parsing a prose code fence. Handle refusals and incomplete responses explicitly; [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) constrain shape but do not establish semantic correctness.

The response may contain target subtree replacements or additions, permitted component/instance operations, typed state/breakpoint styles, responsive relationships, declared form behaviors, custom module source, asset-generation requests, verified component-selection references, proposed identity/decision records, design criticism, required user information, and conflicts. Relate results and conflicts to the corresponding requirements and target IDs. Every requested region must have a result or an explicit conflict; unresolved required targets block Apply, and a partial response cannot silently omit a filled region. It cannot contain executable filesystem patches, arbitrary commands, installations, or edits outside the permitted IDs. Shared-definition/token/route/ancestor changes require an explicitly broader user-selected scope and review. Merely reading a component definition or another page does not authorize changing it. New local definitions may be introduced only for the authorized target instances.

Run each job through these steps:

1. Validate the request, included page/instance scope, accepted decisions/exceptions, brief protections, key availability, limits, and estimated cost across the planned text steps. Create the immutable REQUIREMENTS.md and attachment manifest; persist job intent and the document hash before making a paid request.
2. Analyze the input's implementation, component, and identity needs against that document. Resolve component requests through the qualified catalogue; return explicit conflicts for unsupported dependencies or identity contradictions. Generate the actual implementation using the verified results and the same requirements file. Stream progress without applying partial changes, then parse and validate the complete typed candidate and its proposed project-memory changes.
3. Present any proposed image jobs with their model, count, dimensions, quality, and estimated cost. Obtain the user's image-cost approval or use a previously configured explicit per-job allowance. Keep existing assets when the user declines a replacement.
4. Generate approved images, save actual returned bytes, and bind asset IDs. Resolve required user inputs and conflicts. A candidate with missing required assets or behavior cannot become ready.
5. Compile real custom code and the render representation. Resolve shared definitions, state styles, internal links, fonts, and assets. Render affected pages and affected shared instances at their reference sizes and review widths; run structural, protection, overflow, accessibility, explicit layout-constraint checks, and review relative-placement fidelity under the single job mode. Do not enforce prompt text-box dimensions as site dimensions.
6. Present the working candidate with Apply/Discard, affected pages/instances, chosen components, proposed identity/PROJECT.md changes, design criticism, and unresolved configuration findings. Let users retain intentional creative choices within valid requirements. Revalidate scope and current project state when Apply is pressed, durably checkpoint the current project, and commit site changes and accepted decisions in one transaction. Desegnos regenerates PROJECT.md from the committed data; it never rewrites the original job's REQUIREMENTS.md after acceptance.

Only one generation job runs per project. Each job uses target-page/subtree, annotation text/placement, the selected global mode, ancestor-layout, component-definition, instance-override, brief/protection, route, font, and shared-token hashes in addition to the base revision. Unrelated manual edits may coexist if the job's read dependencies and targets are unchanged. If they changed, the candidate becomes stale and requires regeneration or an explicitly reviewed conflict resolution. The review cannot broaden scope automatically. A revision number alone cannot prove a safe merge.

Record each applied job ID in the command transaction so retries or repeated Apply clicks cannot duplicate changes. Cancellation invalidates the local job result even if a late provider response arrives. Discard never creates document mutations. Keep completed paid image results available for an explicit retry of a failed job instead of purchasing them again.

Accepted decision/exception hashes, qualified component versions, and REQUIREMENTS.md attachments join the existing read-dependency set. Changing a relevant decision or component while a job runs makes it stale; unrelated notes do not. A retry reuses the original requirements snapshot unless the user explicitly starts a new job from changed requirements. Markdown content remains untrusted task data and cannot grant tools, install dependencies, expose credentials, or alter native permissions.

A component that requires a backend must identify the real endpoint and expected response. Browser-exposed service credentials are never presented as secure secrets. Do not claim successful submission or authentication without actually verifying the configured service.

External links and downloads use a trusted host confirmation that shows the destination before opening the browser or a save dialog; a frame message alone is never authorization. Do not enable unrestricted top navigation or popups to make a test pass. Opaque-origin previews restrict browser storage; components requiring persistent browser storage must report that capability requirement rather than silently substituting a different behavior. Client-only state and browser-compatible public endpoints are the guaranteed custom-code contract for 1.0.

The app bundles the compiler and supported modules for offline preview. Generated code may not import remote modules, run package scripts, start a process, or install dependencies. ## 9. Preview and native security

Treat generated markup, CSS, scripts, SVGs, projects, and provider responses as untrusted inputs. This security boundary is part of the functional release, because users are deliberately running generated code.

The inline frame starts with `sandbox="allow-scripts"` without `allow-same-origin`. Enable `allow-forms` only in Preview mode after the user has enabled a declared real form destination; restrict `form-action` to those exact HTTPS destinations and otherwise set it to `none`. Apply a restrictive CSP: default deny, compiled scripts only, registered preview resources and packaged image/style/font/media data, no remote frames, no object/embed, no top navigation, and no privileged native protocol URLs. A dedicated resource scheme serves only session-approved immutable site bytes and validates byte ranges. External network origins are blocked by default and must be explicitly declared and enabled for a real integration. Never add a Rust HTTP proxy to bypass browser CORS or pass the OpenAI key into generated code. MDN explains the [iframe sandbox boundary](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

Host/frame communication is a small protocol for rendered bounds, selection hints, focus, runtime errors, and internal preview-navigation requests. Validate the actual source window, session, project revision, page/instance/node IDs, message size, rate, and payload shape. Internal navigation can select only pages/anchors in the frozen preview package. Frame messages cannot authorize project edits, file writes, credential access, external navigation, or updates. The trusted overlay makes edits through validated Rust commands; external actions require the trusted user confirmation described above. Consider reported geometry untrusted and constrain it to the visible page.

Explicitly register application-command permissions using Tauri's application manifest and grant them only to trusted editor windows. Do not assume custom `invoke_handler` commands inherit a secure default: [Tauri documents that they are allowed to all windows unless configured](https://v2.tauri.app/security/capabilities/). Detached preview windows receive no application, filesystem, credential, shell, or updater capabilities. Native commands also validate caller labels, IDs, revisions, and resource scopes.

Use a patched, pinned Tauri/Wry combination, keep IPC initialization out of untrusted frames, and test attempts to invoke both Tauri APIs and raw WebView IPC. Origin checks alone are insufficient on Linux, as Tauri's capability documentation warns. The prior [iframe IPC advisory](https://github.com/tauri-apps/tauri/security/advisories/GHSA-57fm-592m-34r7) explains why patched initialization and invoke-key protections matter. A successful privileged call from generated code blocks release.

A sandboxed iframe does not guarantee separate CPU or crash isolation. Keep durable state and an editor-heartbeat watchdog in Rust. A native Reload Workspace action must recreate an unresponsive webview from the last committed state without rerunning the offending component. After a missed heartbeat, offer this recovery through native UI; start the recovered page with scripts paused until the user chooses to resume. Prove recovery from an infinite loop and renderer crash on each operating system. An inability to recover is an architecture failure to fix before release.

Default diagnostics contain error codes and local job IDs, not keys, full prompts, source, or images. User-exported diagnostics show a redacted preview first. Opening a project created elsewhere shows that it contains custom code and leaves scripts paused until the user chooses to run it. That choice grants execution in the restricted preview, never native privileges.

## 11. Accessibility and quality budgets

## 16. Public release checklist

Publish 1.0 only when all of the following are true:

1. The final name has passed the recorded clearance review, identifiers are reserved, and the actual icon and brand assets are complete.
2. Every release-contract capability works in the real desktop app. No dead controls, mock providers, temporary asset URLs, incomplete export files, fabricated results, or unimplemented advertised integrations remain.
3. Actual OpenAI text generation, scoped revision, image generation, and image editing have passed with a real test account. Cost and uncertain-outcome handling are verified.
4. Multi-page authoring, paths, navigation, anchors, home/404 selection, component definitions/instances/overrides, and shared styles work across the included site.
5. Desegnos maintains PROJECT.md from accepted decisions and sends an actual immutable REQUIREMENTS.md on Generate. Identity/component/implementation responsibilities, qualified component reuse, creative critique/exceptions, and atomic site/notes updates pass; protected text/assets/subtrees remain protected through indirect shared changes in both modes.
6. Inline prompts, a sidebar-free editor, one global Strict/Fuzzy job setting, agent-coordinated responsive layouts, full visual editing, overlapping content, actual interaction states, real form responses, and custom code pass their scenarios.
7. Fonts, responsive image variants/originals, supported audio/video/captions, actual favicon/search/sharing metadata, robots rules, and the real sitemap survive save/reopen and both exports.
8. Named and automatic checkpoints survive reopen, compare and restore complete project/asset state safely, and never replay an AI job or rewind the job ledger.
9. The site check exposes actionable real findings for every included page, never submits forms automatically, and reports unverified conditions honestly.
10. Both complete site exports work independently, preserve links/assets/metadata/states/behavior, pass direct-file and hosted tests as specified, and contain correct licenses without editor code leakage or privileged evaluation of custom modules.
11. Saves, recovery, undo/redo, stale jobs, cancellation, malicious inputs, sandbox/resource isolation, and hung-preview recovery pass.
12. Accessibility and measured single-page/whole-site performance meet the stated budgets or the implementation is corrected before release.
13. Every advertised native target has installation and update evidence. Packages carry the required OS signatures and notarization, and updater signatures validate.
14. The exact release artifacts match the tagged source and recorded dependency locks; hashes, source, notices, SBOM, documentation, screenshots, and full-site demo are published together.
15. Release jobs require protected approval, signing secrets remain protected and backed up, and rollback plus security-reporting procedures are usable.

After publication, reproduce reported regressions against the released build, preserve recovery paths, and patch security or data-loss failures promptly. Model catalogue changes require the relevant live generation and full-site export checks before a release advertises support.

## 17. Further user needs

The accepted 1.0 scope includes all seven added feature groups and the project brief. [Further feature research](FEATURE_RESEARCH.md) assesses additional needs, complete implementation requirements, primary-source evidence, and dependencies. Content collections, linked multilingual sites, visitor search, publishing/staging, project-wide find/replace, review workflows, URL migration, and visual animation remain candidates for a separate scope decision. They are not inactive controls or partial implementations in 1.0, and their work is not included in the estimate above.

Prioritize content collections and linked multilingual content for a product decision if blogs/catalogues or translated sites are core target uses. Adding either changes the project model and export acceptance contract, so incorporate it before implementing those boundaries if selected. Preserve ordinary stable IDs and versioned schemas for current requirements; do not build speculative plugin systems or empty modules for unapproved features.

[The plugin review](PLUGIN_REVIEW.md) classifies current features and all eight candidates into core responsibilities, bundled extension candidates, and optional plugins. Requirements assembly, accepted project memory/identity, safe application of changes, saving, preview isolation, and minimum export validation remain core. This classification proposes packaging boundaries; it does not remove a promised 1.0 capability or commit to a public plugin marketplace.
